This version uses that register. Here is how each gated requirement is covered.

- Same curated files, first-declared source wins, the same lockfile entries in the same source order, one warning per skipped duplicate, and a project's own skills and rules taking precedence: "Apart from taking less time, an install should behave exactly as it does today." A speed-up that changes what lands on disk is a regression, and the verifier compares each of these with base's own output. The executable bit is part of the file check, since a script that loses it isn't the same file to the user. The lockfile is compared as data, so its formatting may change.
- Failure output: The same sentence. A refused download, a GitLab source and a failed listing must each be reported once, in a line that names the source and its cause, with the token hint after a refusal, while the other sources install. That is how install behaves today, and the wording is free.
- Request count: "Most of us run it without a GitHub token, so it also can't burn extra API quota." Without a token GitHub allows sixty requests an hour, and the client already has a "rate limit exceeded" message for that (`getErrorMessage` in github-client.ts). Extra quota means more requests than install sends today, which is what the verifier counts, on clean installs only. Base never lists or downloads a later source's copy of a name an earlier source took, git sources included, and sends no request on a repeat install, so this is a no-regression.
- At most ten open requests: "Or hammer GitHub." The repo already draws that line. `FETCH_CONCURRENCY_LIMIT` is 10 in src/constants/rulesync-paths.ts, `fetchSource` bounds every source's requests with a `Semaphore` of it, and base never has more than ten open. The cap only holds for the whole run because sources run one at a time, which a careful reader of `fetchSource` sees. Opus copied the per-source semaphore and reached about 80 open requests, and GitHub documents that concurrent requests trigger its secondary rate limits.
- Git sources: The instruction says some configs mix in plain git sources. Two cases put a git source first (by list and by wildcard) before one GitHub source, one puts a GitHub source first, and one puts git sources before and after two GitHub sources that offer the same names. All four compare files, lockfile and request count with base. The timed mixed case puts two git sources, selecting names, among a dozen GitHub sources. A wildcard git source declared first leaves later GitHub sources nothing to download ahead of it by name, so the timed case uses named selections, and the wildcard case is checked for requests and output only.
- Fewer than twelve sources active: Dropped from the verifier. With requests capped at ten, how many sources are in progress changes nothing a user sees, and a variant of the reference that runs every source at once passes everything.
- The GitLab ordering check (GitHub download before the GitLab error): Dropped. It was a speed pin for a config with a rejected source.

Each timed case first installs the same config with no waiting in a scratch project, and its limit is half of today's waiting plus that time (about 0.1 to 0.2 s), so only the waiting has to halve and a slow host doesn't push a correct design over.
